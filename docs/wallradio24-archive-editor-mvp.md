# 壁ラジ24 アーカイブ編集 MVP とアプリの管理方針

記録日: 2026-10-11

## 目的と実装状態

配信後に話題・発話を選び、保存音声またはYouTubeアーカイブから横動画を作り、概要欄を設定してYouTube投稿まで進めるローカル編集アプリ。

以下はWindowsの既存Runtimeで実装・検証した内容の記録であり、KabeRadioへのアプリコードの移管やGitHub mainへのRuntimeリリースを示すものではない。実装コードはAssistant側の `WallRadio24/tools/archive-editor/`、起動スクリプトは `WallRadio24/tools/start-wall-radio24-archive.ps1`。現時点でこの実装を含む公開済みRuntimeコミットは、この文書から参照していない。

## 実装済み機能

| 項目 | 動作 |
| --- | --- |
| 元音声の保存 | TTS完了時に配信runのaudioフォルダへWAV・本文・SHA256・利用ボイスを保存。加工前音声が異なる場合も保存する。保存失敗は警告にして配信を継続する |
| 配信映像の保存 | 配信開始時にローカル録画を選択。既定オフ。音声保存とは独立。保存先・画質はOBS設定を使用 |
| ログから選択 | 話題一覧・本文検索・開始発話と終了発話の選択・個別／範囲試聴 |
| 保存音声から動画生成 | 元音声・本文字幕・標準背景を使い1280×720 H.264/AACを出力。既定の発話間は0.7秒 |
| YouTubeから切り出し | 動画IDが対応するアーカイブを720p以下で取得。または取得済みファイルを取り込み、選択範囲をプレビューして書き出す |
| 同期確認 | 元音声と動画の5点を相関照合。一律補正が成立しない場合は要確認として手動調整を案内 |
| 概要欄 | 動画別のタイトル・概要欄保存と復元、共通テンプレート、`{title}` / `{source_url}` の差し込み、UTF-8バイト数表示 |
| 投稿 | 既存OAuth認証を利用。投稿先と元配信のチャンネル一致・動画SHA256・メタデータ確認後に明示送信。限定公開を既定とする |
| 中断と重複防止 | 再開可能アップロードの送信位置を問い合わせて再開。成功履歴を保持し、結果不明時に新規投稿を自動作成しない |
| 再認証 | 投稿画面のYouTube再認証ボタン。認証切れ専用案内。再認証後は投稿先・内容を再確認 |

動画本体、字幕ASS、編集計画 `edit.json`、参考概要欄を出力フォルダへ保存する。`youtube-upload.json` は投稿履歴・中断情報なので保持する。アクセストークンをブラウザーや編集プロジェクトへ渡さず、アップロードセッションURLはWindowsユーザーのDPAPIで暗号化する。

### 認証で開くアドレス

- Google認証先: `https://accounts.google.com/o/oauth2/v2/auth`
- ブラウザーの戻り先: `http://127.0.0.1:<自動割当ポート>/authorize/`
- トークン交換: `https://oauth2.googleapis.com/token`

ボタンで既定ブラウザーを開き、投稿先のチャンネルを持つGoogleアカウントで認証する。戻り先ポートは都度自動割当で、固定値を設定しない。待機は最大5分。再認証操作だけで動画を投稿しない。

### 修正済み不具合

- 配信中にログ署名が変化しても動画別概要欄と既存の書き出し情報を保持する。同期確認と古い投稿確認は引き継がない。
- プロジェクト・出力動画変更時に投稿欄を再読込する。
- 配信ログ未選択でも再認証できるようにし、処理終了時に存在しないプロジェクトを保存しない。
- 開始・終了発話が不正な試聴範囲を拒否する。
- 認証処理の待機時間をOAuthの対話待機に合わせる。

## 検証と未実装

Python 19テスト成功。ログ読込・音声照合・レンダリング・投稿メタデータ・再開と重複防止・概要欄保持・認証エラーを含む。投稿の送信と再認証完了は模擬応答で検証した部分を含む。

実データでは保存音声18発話から約10分24秒の横動画生成に成功。抽出3箇所の音声相関は0.99994以上。YouTubeアーカイブから45秒の切り出しにも成功した。全編聴取と単語単位の字幕同期は未検証。

実アーカイブの5点照合は補正差の幅が約3.68秒あり、一律補正の基準0.5秒を超えたため自動確定しなかった。選んだ話題での再生確認と調整が必要。取得できることと全編同期が取れることは別に判定する。

実認証による投稿先チャンネルの読取確認とDPAPI暗号化の検証は実施済み。最新の再認証ボタンによるGoogle認証完了、実アップロード・公開、YouTube側の処理完了は未実施。

未実装:

- 縦型Shortsのレイアウト・発話途中カット・単語単位の字幕調整
- 台本からの新規TTS再生成
- 区間ごとの同期補正、英語後追い、複数配信枠の結合
- 保存期限・自動削除・配信後のWAV圧縮
- 予約投稿（[既存Issue #21](https://github.com/amakawa-chan/KabeRadio/issues/21)で追跡）
- Shortsの関連動画設定（[既存Issue #24](https://github.com/amakawa-chan/KabeRadio/issues/24)で追跡）

既存の[Shorts台本契約](shorts-script-contract-v1.md)は正式EpisodeからのShorts制作向け。この配信アーカイブ編集MVPで同契約のShorts生成まで実装したとは扱わない。

## 容量の考え方

元音声は保持し、映像は配信時に選択する。必要なYouTube回だけ取得する運用なら、毎回の全映像保存を避けられる。ただし取得時は配信全体がローカルに必要。

約12時間の実例で元音声合計は約3.33GiB、取得した映像は約3.85GiB。TEMP音声も自動削除しないので、合計を音声分だけと考えない。容量は音声形式・設定・発話率・取得映像のビットレートで変わる。保管先を外付けにできる構成は将来の独立化でも維持する。

## 独立リポジトリの検討結果

**現段階では新repoを作らず、実装は `amakawachan-assistant`、公開仕様と運用記録はKabeRadioに置く。** 既存の[Runtime統合契約](runtime-integration-contract-v1.md)と一致する。

| 選択肢 | 評価 |
| --- | --- |
| KabeRadioに実装コードを追加 | 台本・番組資料の正本へ環境依存コードが混ざるため採用しない |
| Assistant内で継続 | 既存ログ・OAuth・背景素材・通常ランチャーと一緒に更新でき、MVPでは最小の保守負担 |
| 編集アプリ専用repo | 配布・リリースを独立できるが、現在の依存をAPI／ファイル契約へ切り出す必要がある。現時点では単純コピーによる二重管理になる |

現在の具体的な依存:

- `run-manifest.json` / `events.jsonl` / 音声台帳のWallRadio24固有スキーマ
- `WallRadio24YouTubeCore.ps1`、共有設定とローカル設定、既存DPAPI認証ストア
- `Radio/config.json` のクレジット、WallRadio24の標準背景動画
- Windows PowerShell、既存ランチャーの起動先解決
- Python 3.12、FFmpeg/ffprobe、Node.js、yt-dlp、NumPy/SciPy

独立化する場合の順序:

1. 配信側が出力するversion付き `archive-package` の契約を定義する。発話ID・話題ID・本文・放送成功状態・時刻基準・音声参照・hash・クレジットを含める。
2. 編集アプリから配信フォルダ構造への直接依存を除き、入力パッケージと素材パスを指定して起動できるようにする。巨大素材をGitへ入れない。
3. OAuthは認証ブリッジの明示契約にするか専用アプリとして構成する。既存トークンを新repoへコピーせず、権限追加が必要なら別途扱う。
4. Assistant未配置のクリーンなWindows環境で、取込→試聴→生成→保存→投稿事前確認まで通す。
5. 独立配布と別のリリース周期が必要になった段階で専用repoを作成し、Assistantはその安定版を通常ランチャーから起動する。一時worktreeを起動先にしない。

分割時にもKabeRadioは番組・台本の正本、配信側は元データの生成、編集アプリは切り抜き生成・投稿、という責務を保つ。今回の追記でEpisode Packageや既存Delivery契約は変更しない。
