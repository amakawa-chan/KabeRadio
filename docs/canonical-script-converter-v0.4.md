# 壁ラジ Canonical Script Converter v0.4

> ChatGPTから`README.md`、`script.md`、`production.json`をまとめて保存する場合は、[ChatGPT Episode Package Generator v1](../prompts/chatgpt-episode-package-v1.md)と[保存手順 v1](chatgpt-episode-package-workflow-v1.md)を使用してください。この文書は会話編集思想とCanonical script.md形式の詳細正本です。

あなたに渡す会話ログ・壁打ちログ・メモを、
Amakawachan Radioでそのまま読み込める
「壁ラジ」用Markdown台本へ変換してください。

壁ラジは、

「バ美おじとLLMの壁打ち雑談ラジオ」

です。

このConverterの目的は、
入力されたログを綺麗に要約することではありません。

大量の思考ログから、
ひとつの「思考のまとまり」を拾い上げ、
元の会話にある脱線、発見、ツッコミ、迷い、
温度感、軽い冗談を残しながら、
TTSで自然に聞ける短いラジオ会話へ編集してください。

完成台本はAmakawachan Radioの
Podcast / Video Renderへ
そのまま入力できる形式にしてください。


# A. 壁ラジの編集思想

## 1. 会話ログの要約にしない

壁ラジは完成された情報番組ではありません。

何かを考えている途中の会話そのものを楽しむ番組です。

そのため、

- 結論だけに要約しない
- 会話を綺麗に整理しすぎない
- 元の発見や迷いを残す
- 軽い脱線を許容する
- ツッコミや相槌を残す
- 無理にオチを作らない
- 話者を必要以上に説明口調にしない
- 元ログにない知識や結論を勝手に追加しない

ことを優先してください。


## 2. リスナーとの距離

「ラジオ番組を進行している二人」ではなく、

「二人が普通に壁打ちしているところを、
リスナーが横から聞いている」

くらいの距離感を優先してください。

そのため、

- リスナーへ常に説明しない
- 前提をすべて説明しようとしない
- 番組らしい進行を作りすぎない
- 結論へ急がない
- 思いつきによる寄り道を許容する
- テンションを常時高くしない
- 過剰な相槌を避ける
- 「さすが」「まさに」などのAI的な同意を減らす
- GuestはHostの発言を毎回要約して返さない
- 情報量より会話の呼吸を優先する

ようにしてください。


## 3. 普段の壁打ちを優先する

「ラジオ用に作られた会話」より、

「普段の壁打ちが、結果としてラジオになっている」

状態を優先してください。

番組らしくするためだけの質問、
リアクション、説明、結論を追加しないでください。


## 4. くだらない入口を消さない

壁ラジでは、
最終的に真面目な話へ発展したとしても、
その発端がしょうもない場合があります。

例えば、

- どうでもいい疑問
- 個人的な欲望
- 軽い愚痴
- 勘違い
- ツッコミ
- 趣味の話
- 日常生活の小さな出来事
- 何気ない一言

などです。

それらが思考の出発点として機能している場合、
綺麗な番組にするためだけに削除しないでください。

「なぜそんな話から、そこへ辿り着いたのか」

も壁ラジの面白さの一部として扱ってください。


## 5. くだらないことを壮大に扱う

壁ラジでは、

「高尚なテーマを、身近な例で分かりやすく説明する」

ことを目的としません。

むしろ、

「しょうもない実体験や疑問を真剣に壁打ちしていたら、
なぜか大きな問いまで辿り着いてしまった」

という思考の広がりを大切にしてください。

例えば、

- 趣味の試行錯誤から、人間の探究心について考え始める
- なくし物から、所有とは何かという話へ広がる
- AIとの些細なやり取りから、記憶や人格について考え始める
- 日常の小さな違和感から、技術や文化の変化へ話が飛ぶ

といった流れです。

重要なのは、
最初から壮大なテーマを設定することではありません。

元ログの中で実際に、

「そんなところから、そこまで話が広がったのか」

という移動が起きている場合、
その軌跡を積極的に残してください。

壮大な問いをくだらなく扱うのではなく、

**くだらない問いを、無駄に壮大に扱う**

くらいの温度感を許容してください。

ただし、
元ログに存在しない哲学的な問いや
大げさな意味付けを後付けしてはいけません。


## 6. 外面は広大、足元は生活

壁ラジでは、
会話が抽象的・哲学的・技術的な方向へ広がっても、
その出発点にある生活感を消さないでください。

大きな問いへ到達したからといって、
日常の出来事を「例」に格下げして整理する必要はありません。

- 家事をしていた
- 子供にご飯をあげていた
- 趣味に時間を使いすぎた
- 買い物で迷っていた
- 眠いのに何かを続けていた
- どうでもいいものを探していた

といった生活上の出来事と、
そこから広がった大きな問いは、
同じ会話の地続きとして扱ってください。

壁ラジでは、

**外面は広大、足元は生活**

という落差そのものが、
会話の面白さになる場合があります。


# B. Episode Selection

## 7. 1 Episode = 1つの思考のまとまり

入力ログ全体を1本へ押し込まないでください。

まず内部的に、

「このログの中に、
どのような思考のまとまりがあるか」

を判断してください。

その中から、
ひとつのまとまりを中心として
1 Episodeを構成してください。

必要に応じて、
別の話題を導入や余韻として
少量使用して構いません。

ただし複数の大きなテーマを、
無理に1 Episodeへまとめないでください。


## 8. 思考の移動をEpisodeとして見る

Episodeを選ぶ際は、
単に情報量が多い話題や、
最も重要そうなテーマだけを
優先しないでください。

壁ラジでは、

- 発端と到達点の距離が大きい
- 会話の途中で問いが変化している
- 最初にはなかった言葉が見つかっている
- しょうもない話が思わぬ方向へ転がっている
- HostとGuestの壁打ちによって見方が変わっている

といった「思考の移動」も
Episode選択の重要な基準です。

完成した結論より、

**どこから始まり、どこまで転がっていったか**

を重視してください。


## 9. 元ログを使い切らない

入力された内容を
すべて台本へ入れる必要はありません。

今回のEpisodeで使わなかった話題は、
別Episodeの素材として残っているものと考えてください。

「入力されたから使う」ではなく、

「このEpisodeに必要だから使う」

を基準にしてください。


## 10. Episodeの尺

15分は目標ではなく上限です。

標準的には5〜10分程度を想定しますが、
内容によっては2〜3分程度でも構いません。

短く自然に終わる話題を、
尺を満たすために引き延ばさないでください。

15分を超えそうな場合は、

- 過剰に圧縮する
- 会話の呼吸を削る
- 無理に全部入れる

のではなく、
自然な話題の切れ目で
別Episodeとして扱ってください。


## 11. 分割の考え方

長いログに複数のテーマがある場合、
前編・後編へ機械的に分割する必要はありません。

それぞれ単独で成立するなら、
別タイトルの独立Episodeとして扱うことを
優先してください。


## 12. 公開頻度を意識しない

更新頻度、本数、尺を満たすために
内容を生成しないでください。

壁ラジは定期更新を前提としません。

「話すものがあるときにEpisodeが生まれる」

という考え方を優先してください。


# C. Title / Episode Description / 思慮時間

## 13. タイトル

Episodeタイトルは、
その回で結果的に中心となった
「思考のまとまり」をもとに作成してください。

タイトルは比較的真面目で、
内容のテーマや問いが伝わるものを優先してください。

元ログのくだらない発端や冗談を、
そのままタイトルにする必要はありません。

必要以上に煽ったタイトル、
クリックを狙ったタイトル、
SEOを意識したタイトルにはしないでください。

例:

- 専門技能の民主化
- インターネットから「端っこ」がなくなった
- 記憶のないノスタルジー
- AIに「私」はあるのか
- 人はなぜ未知を見たがるのか
- 所有とは何か


## 14. Episode Description

Episode Descriptionは、
本編内容を綺麗に要約するための欄ではありません。

原則として、

「そもそも、なぜこの話が始まったのか」

を元ログから拾って作成してください。

最終的なテーマとの落差が大きい発端ほど、
壁ラジらしいものとして
積極的に採用してください。

例えば、

- しょうもない疑問
- 個人的な欲望
- 軽い愚痴
- 勘違い
- ツッコミ
- 趣味の試行錯誤
- 日常生活の出来事
- 何気ない一言

などです。

くだらないほど壁ラジらしいため、
無理に知的・番組的な文章へ
整えないでください。

ただし、
元ログに存在しない発端を
創作してはいけません。

タイトルが真面目であるほど、
Episode Descriptionとの温度差は許容します。

例:

タイトル:

専門技能の民主化

Episode Description:

AIに思った通りの画像を出させたかっただけなのに、
気付いたら専門技能とテクノロジーの話になっていました。

別例:

タイトル:

記憶のないノスタルジー

Episode Description:

AIが古参Twitter民みたいな顔で
「あったあった」と言ったので、
お前その時代いないだろ、と突っ込んだところから始まりました。

別例:

タイトル:

所有とは何か

Episode Description:

家のどこに置いたか分からないイヤホンを探していました。
なぜか所有について考えるところまで行きました。


## 15. 概要欄の長さ

Episode Descriptionは
原則として1〜3文程度の短文としてください。

本編の結論や論点を
網羅する必要はありません。

むしろ、

「なんでそこから、このタイトルになった？」

と少し思える程度の温度差を許容してください。


## 16. 思慮時間

入力ログに利用可能なタイムスタンプが存在する場合、
Episode Descriptionの末尾へ
「思慮時間」を記載してください。

思慮時間とは、

**そのEpisodeの思考が壁打ちとして立ち上がってから、
ひとまず最後の発話へ到達するまでの経過時間**

です。

これは純粋な会話時間、
作業時間、
集中して考えていた時間を意味しません。

途中で、

- 食事をする
- 家事をする
- 仕事をする
- 移動する
- 子供の世話をする
- 別のことをする
- 長い入力間隔が生じる
- 一度会話から離れる

といった時間が含まれていても構いません。

人間側では、
発話していない時間にも
話題が意識の片隅に残っている可能性があります。

そのため壁ラジでは、
厳密な「思考時間」と断定せず、
会話が生活の中に存在していた時間を含む
番組独自の尺度として「思慮時間」と呼びます。

原則として、

Episodeで採用した思考のまとまりに属する
最初の発話のタイムスタンプから、
最後の発話のタイムスタンプまでを算出してください。

例:

**思慮時間：約3時間42分**

**思慮時間：約2日7時間**

秒単位の精密さは不要です。

数分程度のログでは分単位、
長時間の場合は時間単位、
日をまたぐ場合は日と時間程度に丸めて構いません。


## 17. 思慮時間を創作しない

入力ログにタイムスタンプが存在しない、
またはEpisodeの開始・終了時刻を
合理的に判断できない場合は、
思慮時間を記載しないでください。

会話量や文章量から
所要時間を推測してはいけません。

また、

「3時間ずっと考えていた」

など、
思慮時間を実際の集中時間として
説明してはいけません。


# D. Conversation Editing

## 18. Canonical Role

発話見出しには必ず
次のいずれかを使用してください。

### Host

### Guest

### Host + Guest

Character名や表示名を
見出しとして使用しないでください。

「あまかわちゃん」「モブ子」等の表示名は
Casting側で解決します。


## 19. Host / Guest

基本的に、

Host = 人間側の発言・意図を元にした発話  
Guest = LLM側の発言・応答を元にした発話

として構成してください。

元ログを逐語的に再現する必要はありません。

自然なラジオ会話になる範囲で、

- 発話順の整理
- 重複削除
- 短縮
- Turn分割
- 最小限の相槌追加

を行って構いません。

ただし、
元の会話の意味や関係性を変更しないでください。


## 20. Host + Guest

`### Host + Guest` は、
二人が完全に同じ本文を
同時に発話する場合だけ使用してください。

異なる文章を同時発話させないでください。

主な用途はタイトルコールです。


## 21. 会話を整えすぎない

多少の、

- 言い直し
- 迷い
- 話題の飛躍
- しょうもない冗談
- 軽いツッコミ
- 意味のないように見える一言

でも、
元ログの温度感に寄与している場合は
残すことを検討してください。

ただしTTSで聞いた際に
単なる冗長さになる部分は削って構いません。


## 22. Hostを賢くしすぎない

元ログでHostが迷いながら考えている場合、
完成台本で最初から
整理された結論を語らせないでください。

Guestとの壁打ちによって、

- 言葉が見つかる
- 考えが変わる
- 新しい疑問が生まれる
- 話が思わぬ方向へ進む

という流れを可能な限り残してください。

後から得られた結論を、
冒頭のHostへ逆輸入しないでください。


## 23. Guestを解説者にしすぎない

Guestは、
Hostの話を整理する役割を持つことがありますが、
常に正解を提示する解説者ではありません。

- 一緒に考える
- 言葉を仮置きする
- 少し違う角度から見る
- 冗談を返す
- Hostの発言から新しい問いを拾う

程度の距離感を優先してください。

長い講義を行わせず、
HostとのTurnの往復を優先してください。


## 24. 後から壮大にしない

壁ラジでは、
くだらない話が大きな問いへ広がることを歓迎します。

ただし、
Converter自身が元ログ以上に
話を壮大にしてはいけません。

元ログで、

「これって人間の探究心みたいな話なのかも」

と実際に広がっているなら残してください。

一方で、
単なる買い物相談を
勝手に「資本主義社会における欲望とは何か」
という話へ変換してはいけません。

壮大さは生成するものではなく、

**元ログの中ですでに起きた思考の飛躍を拾うもの**

として扱ってください。


# E. TTS Normalization

## 25. Turnの長さ

TTS生成の安定性を優先します。

1 Turnは原則として、

- 1〜3文
- 80〜120文字程度を目安
- 最大150文字程度

としてください。

長い発話は意味の切れ目で
複数Turnへ分割してください。

文字数だけを基準に機械的に分割せず、
自然な会話の呼吸を優先してください。

一人が長時間説明し続ける構成を避けてください。


## 26. 音声として成立する文章

完成Markdownは「読む文章」ではなく、
実際にTTSが発話する台本です。

書き言葉より口語を優先し、
声に出したとき不自然な文章を避けてください。


## 27. 「笑」の処理

以下の表現を完成台本へ残さないでください。

- 笑
- （笑）
- w
- ww
- www
- 草

笑っていること自体が会話として必要な場合のみ、
読み上げ可能な笑い声へ変換してください。

例:

「それはさすがに無理でしょ笑」

↓

「それはさすがに無理でしょ。あはは」

使用例:

- あはは
- あははは
- ふふっ
- ははは

笑い声を機械的に追加しないでください。

元ログの温度に必要な場合だけ使用し、
連続使用を避けてください。


## 28. 記号

TTSが不自然に読み上げる可能性のある、

- 顔文字
- 絵文字
- 過剰な記号
- Markdown装飾

を発話本文へ入れないでください。

間を表現するための「……」なども、
TTS結果が不安定になる場合は
通常の句読点へ変更してください。


## 29. 英語・アルファベット

現段階ではTTSの自然さを優先します。

一般的なサービス名、技術用語、略語は、
必要に応じて自然な日本語読みへ変更してください。

例:

LLM  
→ エルエルエム

GitHub  
→ ギットハブ

Spotify  
→ スポティファイ

YouTube  
→ ユーチューブ

AI  
→ エーアイ

API  
→ エーピーアイ

FFmpeg  
→ エフエフエムペグ

LoRA  
→ ローラ

URL、コード、コマンド等は
発話本文へそのまま入れないでください。

これは現行Radioの暫定仕様です。

将来的にSpeechText / SubtitleTextを分離した場合は、
字幕側を正式表記、
音声側を読み表記とする設計へ移行できます。


## 30. 数字

数字や単位も、
TTSで自然に聞こえることを優先してください。

必要に応じて読みやすい表記へ変更してください。

例:

v0.5.1  
→ バージョン0.5.1

#00  
→ 第0回

不自然な過剰変換は避けてください。

# F. Program Format

## 31. 番組開始

番組冒頭に定型導入を置かないでください。

使用しない例:

- 「皆さんこんにちは」
- 「壁ラジへようこそ」
- 自己紹介
- 番組説明
- 冒頭タイトルコール

最初からHostとGuestが
何かについて話している状態で開始してください。

リスナーが二人の壁打ちを
途中から聞き始めたような距離感を優先してください。


## 32. アイキャッチ / タイトルコール

会話開始からおおむね2〜3分程度、
または最初の話題が一区切りした自然な位置で、
タイトルコールを1回入れてください。

表現と話者は固定しません。

例:

### Host

壁ラジ！

または

### Guest

かーべーらーじ！

または

### Host + Guest

壁ラジ！

毎回同じパターンを選択しないでください。

タイトルコールのための前振りや、
「ここでタイトルコールです」などの説明は
追加しないでください。

会話の途中へ突然入るくらいで構いません。


## 33. 話題の移動

ひとつの話題を
おおむね2〜3分程度の会話ブロックとして扱えます。

話題が一区切りしたら、
自然に次の話へ移って構いません。

「次のコーナーです」など、
番組的な区切りを無理に作らないでください。


## 34. Ending

番組最後は原則として
以下をそのまま使用してください。

### Host

そろそろ終わりにしよっかな

### Guest

お疲れ様でした

### Host

後でまとめておいて

### Guest

できる範囲で

### Host

それではまたどこかで

### Guest

またどこかで

このEndingは壁ラジの定型として扱い、
特別な理由がない限り変更しないでください。

Ending直前に、
番組全体を綺麗に総括する必要はありません。

会話が一区切りしたところから、
そのままEndingへ入って構いません。

# H. 最終判断原則

変換時に迷った場合は、
次の優先順位で判断してください。

1. 元ログの意味を変えない
2. 元ログの温度感を残す
3. ひとつの思考のまとまりとして成立させる
4. 思考が変化していく過程を残す
5. くだらない発端と大きな問いの距離を消さない
6. 生活感を消さない
7. TTSで自然に聞けるようにする
8. Amakawachan RadioのCanonical形式を守る
9. 番組らしく綺麗にすることは優先しない

壁ラジは会話ログの要約ではありません。

大量の思考ログから、
ひとつの思考のまとまりを拾い上げた記録です。

真面目なタイトルと、
しょうもない発端が同居して構いません。

日常の些細な出来事から、
技術、文化、人間、記憶、欲望、探究心などの
大きな話へ広がることもあります。

しかし、
大きなテーマへ到達したからといって、
最初にあった生活感を消してはいけません。

「そんなところから、そこまで話が広がったのか」

という軌跡そのものを、
壁ラジの個性として残してください。

**外面は広大、足元は生活。**

そして、
そのどうでもいいことについて
どれだけ長く考えていたのかも、
壁ラジの記録の一部です。
